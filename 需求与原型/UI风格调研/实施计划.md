## 2. 范围与目标

### 2.1 实施目标

在不改变 v1.0.0 业务范围、数据模型和核心交互规则的前提下，将当前浅灰背景、白色大圆角卡片和亮蓝强调色的交互原型，改造成 UI 风格调研中定义的“蓝调独立志”视觉：深蓝页头与底栏、纸白内容区、蓝白边缘、粗体中文标题、少量黄色和粉色装饰、唱片封面式餐品排布。

完成后，v1.0.0 内部的可交互原型、五张静态原型图和 PRD 附录截图应保持一致；首页、点餐、选餐、待办、我的五页原有功能及跨页面数据联动应通过回归验证。

## 4. 推荐实施方案

### 4.1 方案概述

采用“保留业务内核，替换展示层”的方案：

1. 先在 `index.html` 建立统一页头、纸白内容区、页面辅助标签和装饰节点，保留所有现有 ID、页面 `data-page` 和表单/弹窗语义。
2. 在 `app.js` 中只调整动态 HTML 模板和状态属性，使餐次编号、分类选中态、任务状态、导航状态和动态日期可由 CSS 稳定表达；数据和事件流程保持不变。
3. 在 `styles.css` 中建立新设计变量和共用组件，再逐页校准。页面使用深蓝外壳与页头、纸白内容区、1–1.5px 深蓝边框、黄色选中态和低强度粉色装饰。
4. 从现有本地原型图提取九种餐品与头像为独立图片，摆脱整页截图的固定背景坐标；水果继续保持无数据状态。
5. 完成所有功能态和响应式回归后，再导出五张正式原型图，并同步交互原型参考图和 PRD 附录，确保同一版本只有一套最终视觉。

业务数据流保持为：用户操作 → 更新现有 `state` → `saveData` → `renderLinkedViews` 或当前页渲染 → Toast/页面状态反馈。视觉改造不引入第二套状态管理。

### 4.2 关键决策

| 决策 | 选择 | 理由 | 替代方案及不采用原因 |
| --- | --- | --- | --- |
| 代码改造方式 | 在现有三个文件上定向改造，不另建新原型 | 当前原型功能完整且业务逻辑集中；可减少双版本漂移 | 复制整套“新版原型”会产生两个 v1.0.0 真源，并增加后续同步成本 |
| 视觉结构 | HTML 提供稳定语义结构，CSS 负责纹理、边缘与装饰 | 可避免用伪元素承载必要文字，也能保持可访问性 | 全部通过 CSS 覆盖无法可靠表达动态日期、餐次编号和目标餐次提示 |
| 动态代码范围 | 只调整渲染模板、展示格式和 ARIA 状态 | 新 UI 的动态列表需要新类和状态属性，但业务规则无需改变 | 完全不改 JS 会迫使 CSS 依赖脆弱的元素顺序；重写 JS 则风险过大 |
| 餐品与头像素材 | 从现有本地原型图提取为独立 PNG/WebP 文件，并保留源参考图 | 避免背景位置随尺寸变化、修复牛奶旧删除标记混入、改善缺图占位 | 继续裁切整页截图会让新原型依赖旧 UI；使用远程图片违反离线要求 |
| 背景纹理 | 使用 CSS 渐变和低透明度重复纹理 | 离线、可缩放、无品牌素材风险 | 直接复用参考站背景图不适合本项目，也增加外部素材依赖 |
| 装饰英文 | 保留为非必要辅助文字，必要时短屏隐藏 | 能传达风格但不影响中文任务完成 | 用英文替换中文标题会降低可用性；完全取消会削弱效果图识别度 |
| 底部导航 | 保留按钮与事件绑定，改为蓝底、黄色选中块 | 不改变路由和交互，满足 `C-09` | 改成链接或新路由没有业务收益并可能影响 Hash 行为 |
| 静态图与 PRD 同步时机 | 所有交互和响应式回归通过后一次性更新 | 避免测试期间截图反复失效 | 边开发边替换 PRD 会造成重复工作和中间版本不一致 |
| 执行拆分 | 两份执行计划：原型实现；验收与版本产物同步 | 两阶段有清晰依赖和独立交付边界，PRD 同步必须等待原型定稿 | 单份计划会把 DOCX 与截图更新混入实现过程，不利于回退和验收 |

### 4.4 接口与数据变化

无外部接口、服务端接口、存储结构或数据迁移。

- `STORAGE_KEY` 保持 `personalAppPrototype.v1`。
- `meals`、`tasksByDate`、`profile`、`targetMeal`、`selectedCategory`、`mealEditMode` 等状态字段保持原结构和语义。
- 食物目录 ID 与分类不变；新增的独立图片文件沿用 `foodId` 命名关系，CSS 或展示辅助函数由 `foodId` 选择资源。
- Hash 和页面名不变，已有收藏地址与浏览器前进/后退继续兼容。
- 可能新增的 DOM 节点只承载日期、英文副标题和装饰，不写入 localStorage。
- `aria-current`、`aria-pressed`、`aria-hidden` 等属性属于展示与可访问状态，不参与业务数据。

### 4.5 关键流程、异常与边界

1. **应用初始化**：加载默认数据并合并合法本地数据，进入 Hash 指定页面或首页；新页头与背景不影响原初始化顺序。
2. **首页**：显示设备当天日期、未完成任务计数与前两条、固定午餐 12:00 与前三项；完成任务后继续从首页移除并同步待办页。
3. **点餐**：三餐以编号标题和封面式网格呈现；修改/完成切换保留；编辑态每条记录显示独立深红删除入口；添加按钮仍写入正确 `targetMeal`。
4. **选餐**：黄色目标条由 `targetMeal` 动态输出；左侧唯一分类选中；添加后仍停留并显示 Toast；直接进入时继续兜底午餐；水果保持空状态。
5. **待办**：日历月首与天数算法不变；选中日期通过蓝底与黄色底线表示；输入、空输入错误、完成与恢复及首页联动不变；长任务由单行截断改为允许换行，但仍保存最多 50 字符。
6. **我的**：保留小满、脱敏手机号和原头像；装饰海报在短屏或大字体时降级；退出弹窗保留取消、遮罩、Esc、确认四条路径和焦点恢复。
7. **导航**：主页面只高亮一个底栏项并同步 `aria-current`；选餐隐藏底栏；底栏不能遮挡内容底部。
8. **素材缺失**：餐品图或头像加载失败时保留固定容器、中文名称和操作，使用纸白/浅灰占位，不导致布局收缩。
9. **存储异常**：继续静默保留内存状态，不因新视觉增加网络或错误页。
10. **长内容与小屏**：三列餐品名称和选餐长名称可换行；六行月份、50 字符任务、200% 文字及 360×640 短屏允许纵向滚动，重要按钮可达。
11. **减少动态效果**：`prefers-reduced-motion: reduce` 下关闭页面进入、弹窗、Toast 和错误摇动等非必要动画，状态仍即时可见。

### 4.6 兼容、迁移与回退

无需数据迁移。用户已有 `localStorage` 会由相同键和相同清洗逻辑继续读取。

实施前记录目标文件与原型图的文件哈希；每个执行阶段只修改本阶段登记文件。若新视觉影响核心流程或在任一目标宽度出现 P0 问题，回退本阶段 HTML/CSS/JS 变更及新增资源，不清理用户数据；静态原型图和 PRD 只在最终验收通过后更新，因此实现阶段失败不会污染版本文档。

项目没有可用 Git 基线时，回退不能依赖 `git reset`。执行阶段应在 `TEMP` 中保存本次修改文件的任务专用备份或通过明确补丁记录恢复，任务完成后再清理；不得覆盖或删除无法确认来源的用户改动。
